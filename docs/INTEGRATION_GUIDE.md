# Integration Guide

CER applications are separate modular monoliths. They integrate through **versioned REST** and **signed webhooks in both directions**, and through nothing else: no shared database, no event bus, no message broker. This guide describes the primitives in `app/core/integration` and the conventions that make them interoperable.

## 1. API surfaces

| Surface | Prefix | Audience | Authentication | Stability |
|---|---|---|---|---|
| Internal UI API | `/api/<module>/...` | this application's own frontend | session cookie + CSRF | changes with the UI (deployed together) |
| Public | `/api/public/...` | anonymous users (login, password reset) | none; explicit whitelist | stable |
| **Integration contract** | `/api/v1/...` | other applications | per-endpoint: webhook signature (future: service credentials) | **versioned** |

Rules for `/api/v1`:

- **Breaking changes create a new version.** Removing or renaming a field, changing a type or meaning, or tightening validation goes in `/api/v2`. `v1` and `v2` coexist until counterparts migrate.
- **Additive changes stay in the version.** Adding optional response fields or new endpoints is allowed in `v1`. Consumers must ignore unknown fields.
- **Tenant from the host.** The tenant is always the subdomain of the host (`https://<tenant>.<app-domain>/api/v1/...`), never a body parameter.
- **Closed surface.** Everything served under `/v1` without a session is enumerated in `tests/test_public_surface.py` (`EXPECTED_VERSIONED_ENDPOINTS`).

Endpoints provided by the foundation:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/meta` | Application name, contract version and tenant subdomain, for counterpart discovery |
| `POST` | `/api/v1/webhooks/inbound/{public_id}` | Receive a signed event from another application |

## 2. Correlation

- **`X-Request-ID`.** Every request gets one: it is generated when absent, returned on the response, written to logs, `audit_event.request_id` and `integration_event.request_id`.
- **`X-Correlation-ID`.** It identifies a business flow across applications:
  - an inbound webhook's value is stored on `integration_event.correlation_id`;
  - outbound deliveries send the value given to `enqueue_outbound(correlation_id=...)`, defaulting to the current request id.

  Pass it along when one event causes another, so the whole chain can be queried with `GET /api/integrations/events?correlation_id=...`.

## 3. Webhook message format

```http
POST /api/v1/webhooks/inbound/we_3f9c... HTTP/1.1
Host: acme.hr.example.com
Content-Type: application/json
X-CER-Signature: t=1726412345,v1=5257a869e7ec...
X-CER-Event-Id: evt_8b1f0c...
X-CER-Event-Type: staffing.employee.hired
X-CER-Source-App: cer-staffing
X-Correlation-ID: 4f2c...

{"employee_ref": "E-1042", "start_date": "2026-10-01"}
```

- **Event type:** dotted lowercase `<app>.<entity>.<action>`, for example `staffing.employee.hired`.
- **Event id:** unique per event and **identical across retries**. Receivers deduplicate on it.
- **Body:** JSON. The signature covers the exact bytes sent.
- **Payload content:** references (ids, codes) plus the facts the receiver needs. Do not copy another application's canonical records wholesale.

## 4. Signature

`app/core/integration/signatures.py`, HMAC-SHA256:

```text
signed_content = "<timestamp>" + "." + <raw body bytes>
X-CER-Signature: t=<timestamp>,v1=<hex hmac>[,v1=<hex hmac>...]
```

- **Timestamp.** The receiver rejects timestamps outside `WEBHOOK_TIMESTAMP_TOLERANCE_SECONDS` (default 300) as replays.
- **Multiple values.** `v1` may appear more than once while a secret is being rotated; one valid match is enough.
- **Comparison** is constant-time.
- **Secret format.** Secrets are generated by the receiver's platform as `whsec_...`. They are shown **once** (on create and on rotate), stored encrypted with the platform master key, and never returned again.

Any language can sign:

```python
import hmac, hashlib, time
ts = int(time.time())
sig = hmac.new(secret.encode(), f"{ts}.".encode() + body, hashlib.sha256).hexdigest()
headers["X-CER-Signature"] = f"t={ts},v1={sig}"
```

## 5. Inbound webhooks

**Setup (receiver side, tenant admin with `integrations.manage`):**

```http
POST /api/integrations/webhook-endpoints
{"name": "Staffing events", "direction": "inbound", "counterpart_app": "cer-staffing",
 "event_types": ["staffing.employee.hired"]}
→ 201 {"public_id": "we_…", "inbound_path": "/api/v1/webhooks/inbound/we_…", "signing_secret": "whsec_…", …}
```

Give the counterpart the full URL (`https://<tenant>.<app-domain>` + `inbound_path`) and the secret, through a secure channel.

**Processing** (`receive_inbound`):

1. **Resolve the endpoint:** active, inbound and belonging to this tenant. An unknown endpoint and a bad signature both answer **401**, so endpoints cannot be enumerated.
2. **Verify** the signature and timestamp.
3. **Validate the event:** `X-CER-Event-Id` and `X-CER-Event-Type` are required, the type must be accepted by the endpoint (**422** otherwise), and the body must be JSON.
4. **Deduplicate** by `(endpoint, event id)` through the idempotency store (scope `webhooks.inbound`). A repeat answers **202** with `status: "duplicate"` and is not processed again.
5. **Handle.** Call the handler registered for the event type **inside one transaction** together with the idempotency record and the `integration_event` row. If the handler raises, nothing is committed and the sender retries.
6. **Unhandled types.** When no handler is registered, answer **202** with `status: "unhandled"`. The event is recorded, so it can be investigated or replayed by the sender.

**CSRF.** Inbound webhooks carry no session cookie, so they are exempt from CSRF by path (`SIGNATURE_AUTHENTICATED_PREFIXES`). Every other mutating API route still requires the CSRF token.

**Registering a handler** in your domain module:

```python
from app.core.integration.webhooks import InboundEvent, register_inbound_handler

@register_inbound_handler("staffing.employee.hired")
async def on_employee_hired(event: InboundEvent) -> None:
    # event.company_id, event.payload, event.correlation_id ...
    await EmployeeRecordsService.open_from_hire(company_id=event.company_id, payload=event.payload)
```

Handlers must be **idempotent in effect** as well. Deduplication covers exact redelivery, not two different events describing the same fact.

## 6. Outbound webhooks

**Setup** (tenant admin):

```http
POST /api/integrations/webhook-endpoints
{"name": "Payroll", "direction": "outbound", "counterpart_app": "cer-payroll",
 "url": "https://acme.payroll.example.com/api/v1/webhooks/inbound/we_…",
 "event_types": ["hr.employee.approved"]}
```

The returned `signing_secret` must be configured on the counterpart's inbound endpoint. When both sides run this foundation, create the inbound endpoint on the receiver first and use *its* secret on the sender. `PUT .../{id}` accepts no secret, so rotate on both sides together.

**Emitting** from domain code, inside the business transaction:

```python
async with transaction():
    await EmployeesDAO.approve(...)
    await enqueue_outbound(company_id=company.id, event_type="hr.employee.approved",
                           payload={"employee_id": emp.id, "approved_at": ...})
```

**Delivery** (`deliver_due`, scheduler job every 30 s, leader instance only):

- **Selection.** Due `pending` deliveries are taken with `FOR UPDATE SKIP LOCKED`, which is safe with several instances.
- **Request.** Deliveries are sent signed, with `X-CER-Event-Id`, `X-CER-Event-Type`, `X-CER-Source-App` (= `APP_NAME`) and `X-Correlation-ID`.
- **Outcome.**
  - A 2xx response marks the delivery `delivered`.
  - Anything else (non-2xx or a network error) retries with exponential backoff: 30 s, 1 min, 2 min… capped at 6 h.
  - After `WEBHOOK_MAX_ATTEMPTS` the delivery becomes `failed`.
- **Inspection.** `GET /api/integrations/webhook-endpoints/{id}/deliveries` shows status, attempts, last HTTP status and error.

## 7. Idempotency for API writes

For `/api/v1` write endpoints that other applications call (and may retry):

```python
from app.core.integration import idempotency

body = await request.body()
key = request.headers.get(idempotency.IDEMPOTENCY_HEADER)
previous = await idempotency.claim(scope="orders.create", company_id=company.id, key=key, request_body=body)
if previous.replay:
    return JSONResponse(previous.body, status_code=previous.status)
result = ...  # perform the write
await idempotency.remember(scope="orders.create", company_id=company.id, key=key,
                           request_body=body, status_code=201, body=result)
```

- **Same key, same body:** the stored response is replayed.
- **Same key, different body:** **422**.
- **Expiry and uniqueness.** Keys expire after `IDEMPOTENCY_TTL_HOURS`, purged hourly. Uniqueness is guaranteed by a database constraint.

## 8. Integration audit metadata

`integration_event` is **append-only** (database triggers) and stores, for every message in or out:

- direction, status (`accepted`, `unhandled`, `duplicate`, `rejected`, `queued`), counterpart application;
- event id and type;
- request id and correlation id;
- a SHA-256 of the body.

It deliberately does **not** store the body. Domain data stays in the owning module.

Changes to webhook endpoints (create, update, rotate secret) are written to `audit_event` with the acting user.

## 9. Capabilities

| Capability | Grants |
|---|---|
| `integrations.read` | List endpoints, deliveries and integration events |
| `integrations.manage` | Create and update endpoints, rotate secrets |

`owner` and `admin` receive both. `manager` receives `integrations.read`.

## 10. Not included (by design)

- A business event bus, Kafka, RabbitMQ or a generic integration platform.
- Service-to-service credentials for `/api/v1` read endpoints beyond webhooks. When a first real contract needs them, add a signed-request or client-credential scheme under `app/core/integration` with tests, and document it here.
- A UI for webhook management. The API is complete; a screen can be added as an administration page when needed.
