## 3. Implementation summary

A Route Supervisor can now open CER Route on a phone, see whether they are already working, press **Start Work**, see their workday state, and press **End Work** — all backed by a real, tenant-scoped, database-enforced domain. Closing the app, losing connectivity, or having the browser session expire mid-shift does not lose or duplicate that workday. A second device resumes the same session instead of creating another one.

No Trip, Activity, or geolocation code was written. A completed Work Session with zero Trips is a normal, tested outcome.

## 4. Work Session model

`app/routers_api/worksessions/models.py` — one table, `work_session`:

| Column | Purpose |
|---|---|
| `id`, `company_id`, `user_id` | Identity. `user_id` references the **Core** user (`user.id`), not `supervisor_profile` — see §5 for why |
| `status` | `active` \| `ended`, `BusinessEnum` + DB `CHECK` |
| `session_date` | Local calendar date at Start Work (D-10). Written once, never recomputed |
| `started_at`, `ended_at` | Server clock, `timestamptz`, authoritative |
| `start_device_captured_at`, `start_utc_offset_minutes`, `end_device_captured_at`, `end_utc_offset_minutes` | Device-reported evidence, never authoritative |
| `vehicle_id`, `mpg_snapshot` | Historical snapshot, nullable, written once at Start Work |
| `version` | Optimistic concurrency (`VersionedMixin`) |

**Why `user_id`, not `supervisor_profile_id`.** Who may *execute* a Work Session is an authorization question (`route.worksession.execute`, granted by role); who has a Route field profile with a vehicle is a separate, optional fact (`supervisor_profile`, RTE02). A user with the capability but no profile gets a perfectly valid session with a null vehicle snapshot — exactly what §6.1 requires. Coupling the session to the profile would have made that impossible without a workaround.

## 14. D-09 — Authentication continuity: decision and evidence

**Inspected first, per the instructions.** `app/routers_api/users/auth.py` confirmed a single stateless JWT (`cer_access_token`), 24 h default lifetime, no refresh mechanism, signed with `SECRET_KEY`, re-verified against `Users.is_active` / `UserCompany.is_active` on every request — no caching.

**Decision: sliding (rolling) expiration, not a refresh token.** `app/core/security/session_renewal.py` (full rationale in its docstring). On any authenticated request that succeeds, if the token has less than half its lifetime remaining, a fresh token is issued with the same identity, reusing `create_access_token`/`set_access_cookie` as-is. No second secret, no revocation list, no new attack surface — the same signature scheme and the same per-request `is_active` checks. Only *when* renewal happens changes: from "since login" to "since last activity."

**Why not a refresh token.** A second token type is real complexity — a secret to protect, a revocation path to maintain — for a requirement ("an actively-working supervisor shouldn't see expiry") that a sliding window satisfies by reusing what already exists. It was rejected as unnecessary risk for the value it would add here.

**Work Session recovery is architectural, not built.** `GET /worksessions/current` is keyed by `(company_id, user_id)`, never by a token or "session ownership" concept. Re-authenticating as the same user — on the same device or a different one — always resolves to the same row. There is nothing to "recover": the mechanism that would need recovering doesn't exist.

**`next=` on the login redirect.** Without it, a Supervisor who lost their session in `/route` would land in `/admin` after re-authenticating (the platform's `DEFAULT_AUTHENTICATED_PATH`) — a jarring discontinuity for a mobile-only role. `AuthMiddleware` (page routes) and the Axios 401 interceptor (API routes) now both redirect to `/login?next=<path>`, and `LoginForm` honors it after success. The path is validated as relative and same-origin before use (`starts with "/"`, not `"//"`) — it is built server-side from `request.url.path`, never trusted verbatim from the client, so there is no open-redirect.

**Revocation.** Unchanged, verified rather than assumed: `test_an_already_open_device_is_rejected_after_membership_suspension` suspends a Supervisor's membership **while their cookie is still cryptographically valid and unexpired**, then proves the very next protected request is rejected (403). A local credential never suffices by itself.

**Tests** (`tests/integration/test_auth_continuity.py`): renewal fires past the half-life threshold; a fresh session is left untouched; a denied (403) request never renews; the `next=` redirect is produced correctly.

## 15. D-10 — Time / timezone: decision and evidence

**Decision: trust the device's reported UTC offset, not its clock.** `_session_date_from()` in `app/routers_api/worksessions/service.py` computes `session_date` from the **server's** authoritative `started_at` plus the device-reported `utc_offset_minutes` — never from the device's own timestamp.

**Why this distinction matters, stated explicitly because it's easy to blur.** A phone's *clock* can drift by minutes or hours — that's the skew edge case, and D-10 is explicit that device time is evidence, not authority. A phone's *timezone setting* is a different, much more reliable signal: it comes from the OS locale, essentially never drifts, and is exactly the piece of information needed to answer "what calendar date did this feel like, locally" — which is the actual question `session_date` has to answer. Trusting the offset while never trusting the clock reading satisfies D-10's guidance precisely rather than by coincidence.

**No company-timezone feature was built.** A field supervisor can work across state lines within CER's multi-state operation; a single fixed company timezone would be actively wrong for that case. Building a timezone-configuration UI would also have been scope the instructions didn't ask for (RTE03's Admin Configuration areas were fixed in RTE02). The device-offset design meets the confirmed requirement — supervisor never configures a timezone, no timezone catalog — without it.

**Honest boundary.** No offset reported (older client, or an action queued while fully offline with no evidence captured) falls back to UTC. This never blocks Start Work or End Work; it is documented, not silent.

**Tests**, all in `tests/integration/test_work_sessions.py`, using `time_machine` with a fresh `TenantClient` minted *inside* each frozen window (documented in the file — freezing the interpreter's clock after login also affects the test client's own cookie-expiry logic, so cookies must be minted at the frozen instant, not before it):

- Friday evening → Saturday morning stays Friday.
- `session_date` follows the offset, not the server's UTC date.
- No offset falls back to UTC without blocking.
- `session_date` is immutable across End Work, even hours later.
- A DST boundary crossed between Start and End does not split the session.
- A device clock reporting the wrong day does not affect `started_at` ordering.

## 18. Offline / durable action implementation

`app/components/react/shared/lib/offlineQueue/offlineQueue.ts` — generic, not Route-specific (RTE04 reuses it for Trip actions without touching this file). Full rationale in its docstring; summary:

- **Durability.** `enqueueAction()` resolves only after IndexedDB confirms the write. The UI never shows "accepted" before that.
- **Idempotency.** Each queued action carries its own UUID, sent as `Idempotency-Key`, reusing the Foundation's existing mechanism (`app/core/integration/idempotency.py`) rather than a parallel one.
- **Ordering.** `flushQueue` sends pending actions **sequentially** (a recursive helper, not a loop — this repository's lint forbids `for`/`of`) and stops at the first failure rather than skipping ahead, so a reordered End-before-Start can't reach the server.
- **Honest boundaries**, stated in the module's own docstring: protected against app kill, tab close, lost connectivity, and cookie expiry mid-queue. **Not** protected against the user clearing site data, browser storage eviction under pressure, uninstall, or device loss/destruction.

`entities/RouteWorkSessions` wires this into Start/End Work: every mutating call goes through the queue, then an immediate flush attempt — online, the difference from a direct call is imperceptible; offline, the action stays queued and `RouteMyRoutePage` shows an honest "queued" state (`start-queued` / `end-queued`) instead of a blank or broken screen, until a background sync (mount, resume, reconnect) confirms it against the server.
